# Durable device authentication

## Existing system

At production base 110485c, browser login (GitHub or a one-use magic link) sets a seven-day HMAC JWT cookie. Browser confirmation authorizes a ten-minute SQLite device code. Polling issues an `access` JWT with a 24-hour expiry; the code can currently be polled repeatedly. CLI login writes only the JWT to `~/.tunn/token` using an atomic 0600 rename. There is no CLI renewal or device revocation. Login nodes own SQLite; other nodes proxy database calls and can forward platform HTTP requests to the login node. Identity validation excludes magic-link/CSRF tokens, but accepts session and legacy access tokens. Publishers authenticate at registration; existing streams do not recheck JWT expiry. TCP exists, but `--account-only` and `connect --account --stdio` are absent in this base.

## Choice and authority

Use per-device rotating refresh credentials with replay detection, issuing five-minute access JWTs restricted to `publish connect`, audience `tunn-tunnels`, purpose `device_access`. The durable credential has no absolute lifetime: daily use and always-on publishing continue until account revocation. Its scope never includes account administration, device management, billing, checkout, pricing, SSH key management, domains, or host reservations. Only tunnel registration and authenticated endpoint access accept the new purpose; all existing account validators continue rejecting it. Browser cookies remain the authority for listing and revoking devices at `/account/devices` with CSRF protection. Legacy clients retain the existing 24-hour response and validation. Updated clients explicitly request durable credentials during code exchange. A code can create only one durable device, atomically with consumption.

The login node owns additive SQLite device and consumed-credential tables, initialized with `CREATE TABLE IF NOT EXISTS` on startup. No destructive schema migration or backfill is needed. Non-login nodes forward durable exchange, refresh and management to the login node; resource nodes verify signed short-lived access tokens locally. Browser management resolves the device owner through the current account email bucket, including merged accounts. No billing files change.

## Rotation, replay and failures

Refresh secrets contain 256 random bits; only SHA-256 digests are stored. Each successful exchange consumes the current secret and records its digest and request ID. Presenting any consumed secret with a different request ID revokes the entire device. A matching request ID may recover the same replacement for as long as that replacement is still current, that is, never redeemed, so a response lost to a network failure or a host sleep of any length is recoverable. Once the replacement rotates, presenting the consumed secret again revokes the device. Access expiry is anchored to the committed rotation or recovery, each of which checks revocation in the same transaction, so an in-flight response cannot extend the revocation bound. The replacement is derived with HMAC-SHA256 under the JWT signing key from the device ID and request ID; the server stores no plaintext secret. This idempotency handles a lost response without granting a general old-token grace period: a consumed secret works only with its own request ID and only until its replacement is used. Consumed digests remain for the device lifetime so replay of older generations is detected. Legitimate clients persist a random pending request ID before sending, and use an OS file lock across processes through response persistence. A client that loses its pending request ID requires a new browser login; credentials are never silently resurrected. Errors explain retry versus `tunn login` recovery without printing secrets or response bodies.

Credential state (server, access token, refresh token, relative expiry converted to a local deadline, device ID and pending request ID) is one atomically replaced 0600 JSON file in a 0700 config directory. The existing `token` file remains a compatibility mirror. Refresh state is bound to the configured HTTPS server; redirects are refused. Separate hosts must use separate `TUNN_CONFIG_DIR` directories. Renew one minute before expiry; local JWT timestamps are not used to schedule renewal, so server/client clock offset does not prevent renewal. A 401 forces one renewal and retry before sending SSH bytes. Connection setup must complete authorization before reading stdin or a local socket.

## Live tunnels and revocation latency

A negotiated `device-reauth-v1` capability allows a second `RegisterClient` containing only a replacement access JWT on the existing control stream. The relay checks the signature, audience, scope, device and email binding and updates the lease without changing registration or pending SSH streams. A separate lease watchdog expires a five-minute lease even if a malicious publisher stops renewing or blocks message delivery; expiry disconnects the publisher and its connections. Older publishers keep their existing behavior. Updated publishers renew in the background and before reconnect; authentication rejection forces one refresh. Temporary refresh failures are reported and retried while the current lease permits; a revoked/replayed credential produces an actionable terminal error.

Relays must synchronize their clocks. Device access allows at most 60 seconds of future issuance skew; a clock-behind relay can therefore add up to one minute to the five-minute revocation bound. Legacy JWT timestamp validation is unchanged. Revocation immediately stops rotation; previously minted tokens can admit new connections for at most five minutes, and a revoked publisher loses its lease within five minutes. Already authorized client SSH streams can drain to their normal end: CONNECT has no in-stream credential update protocol, and refresh never interrupts those streams. This explicit session exception avoids breaking live SSH on normal renewal; it does not permit new sessions after access expiry. Login-node outages fail closed after a publisher lease expires.

## Threat model and audit

A stolen readable credential file can publish/connect as that account until replay is detected or the owner revokes it. Mode 0600, a private directory, atomic replacement, no redirects, TLS and digest-only server storage limit accidental disclosure; they do not protect against malware running as the user or root. Theft of only an access JWT is bounded by five minutes and cannot administer the account. An attacker who exclusively controls a stolen refresh credential may keep renewing until revocation, so the browser device list exposes device ID, creation, last refresh and revoked state. Copying credentials between machines is unsupported; each machine must log in independently. Reuse, creation, rotation and owner revocation produce structured events containing device ID and action, never credentials. Database last-use/revoked timestamps survive restart. A forged device ID or request ID cannot revoke another device without possession of a known credential digest.

This follows the rotation and privilege restriction guidance in [RFC 9700 sections 2.2.2, 2.3 and 4.14](https://www.rfc-editor.org/rfc/rfc9700.html#section-4.14).
